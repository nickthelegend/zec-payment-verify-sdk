判子 · hanko, a seal stamp

Was I paid?

Hanko checks that a shielded Zcash transaction paid you at least the price, with your memo, deep enough and with no transparent part. It needs only your incoming viewing key, which can see payments arrive and can never spend.

One verify() call, five ways in: a Rust crate and CLI, a TypeScript SDK, an x402 paywall, an MCP server for agents, and a dashboard. The same call checks a null-402 Groth16 payment proof against the contracts null-402 deployed on Avalanche Fuji. The core comes from Shielded x402's check_uivk.

Quickstart

Needs Node 22.13+ (the paywall's SQLite store uses node:sqlite), pnpm 10 and Rust 1.89 (pinned in packages/core/rust-toolchain.toml). pnpm test builds the Rust core and every package, then runs the suite against Zcash testnet and Fuji.

  1. Clone and install: pnpm install.
  2. Build and test: pnpm test. Nothing is mocked; the tests read real mined transactions.
  3. Install like a user would: scripts/clean-install.sh packs @zpv/sdk, cargo installs the CLI into an empty directory and verifies a real payment from there.

verify()

verify({ rail: 'zcash' })

Fetches the transaction from lightwalletd, recomputes its txid from the returned bytes, requires that txid in the compact block at the height lightwalletd reports (its time is block_time), parses it with the consensus branch for its height, trial-decrypts every Sapling output and Orchard and Ironwood action with the key, then applies the rules. A bad key, a malformed txid, an unreachable server or an answer that contradicts itself throws; it is never a verdict. Proofs and signatures are not checked: see Trust and limits.

Parameters

  • uivkstringrequired

    The receiver's unified incoming viewing key, uivktest1…. The SDK passes it to the binary in its environment, never on the command line.

  • txidstring, 64 hexrequired

    Display-order txid, as block explorers show it.

  • amountZatnumber | bigintrequired

    At least this many zatoshi must reach the key in outputs that carry the memo.

  • memostringoptional

    Only outputs with exactly this text memo count. Leave it out and every output to the key counts.

  • minConfnumberdefault 1

    0 accepts a mempool transaction, which can still be replaced. Keep it at 1 or more for anything you deliver.

  • allowTransparentbooleandefault false

    By default a transaction with any transparent input or output is refused.

Returns

ok, verdict (paid, refused, or unverified under a cross-check), reasons, paidZat, report (height, confirmations, tip, every decrypted output with its pool and memo, which pools the tx uses) and provenance (lightwalletd, tip, time).

await verify({
  rail: 'zcash',
  uivk, txid: '030c3cbf…8351',
  amountZat: 100_000,
  memo: 'x402z-another-invoice',
});

verify()

Cross-check lightwalletd

One lightwalletd can withhold a transaction, lag behind, or forge one, since proofs are not checked. Pass several and Hanko runs the check against each, in parallel. The answers must agree on the verdict and on what it rests on: found, height, outputs, pools, reasons, amount. Tips and confirmation counts may differ by a block.

Any disagreement, or fewer answers than the quorum, is unverified: ok is false, report is null, and it is never paid. The paywall answers it with 503 and serves nothing.

Options

  • lwdUrlsstring[]or ZPV_LWD_URLS

    Endpoints to ask. They protect you only if different people run them.

  • quorumnumberdefault all

    How many must answer. An endpoint that cannot be reached does not count; one whose answer contradicts itself counts as a disagreement. Every answer must agree, whatever the quorum.

Which endpoints exist

On Oct 22, 2026 hosh.zec.rocks lists two online public testnet indexers: testnet.zec.rocks (lightwalletd) and zaino.testnet.unsafe.zec.rocks (Zaino, same operator), which answered 503 every time we tried that day. Hanko refuses one server under two spellings (with and without :443) as one endpoint twice. The tests that need two agreeing answers fetch from testnet.zec.rocks twice and give both answers to the cross-check rule, and say so. For real independence, run your own lightwalletd or Zaino as one of the endpoints.

verify()

verify({ rail: 'null402' })

null-402 pays per API call with a Groth16 proof of an unspent note on Avalanche. This rail makes three read-only eth_calls pinned to one Fuji block: verifier.verifyProof, pool.knownRoot(root) and pool.spent(nullifier). No key, no gas. @zpv/sdk/null402 runs in a browser.

Parameters

  • proofsnarkjs proof JSONrequired

    proofFromSettleTx(hash) reads one back out of a real settle() call.

  • publicSignalsstring[5]required

    [nullifier, merkleRoot, payTo, requiredAmount, contextHash] as decimal strings.

  • expect.payTostringrequired for ok

    Who you are. Without it and expect.requiredAmount the result is never ok (UNBOUND): a valid, unspent proof that pays someone else is not a payment to you.

  • expect.requiredAmountstring | bigintrequired for ok

    What you charge.

  • expect.contextHashstringoptional

    Binds the proof to one request.

BLOCKEDA proof that passes all three checks is not shown live. It needs a new deposit whose root null-402's operator registers (NULL402_OPERATOR_KEY, not held).
Request
const s = await proofFromSettleTx('0x8596f52d…a593');
const r = await verify({
  rail: 'null402', proof: s.proof, publicSignals: s.publicSignals,
  expect: { payTo: '1257…0813', requiredAmount: '1000' },
});

Surfaces · @zpv/gateway

x402 paywall

A reference HTTP paywall over shielded payments, wire-compatible with Shielded x402: the same x402 v1 envelope under the same zcash-shielded scheme. A test imports Shielded x402's own client module (packages/x402-zcash): its parsePaymentRequired accepts Hanko's 402, and its fetchWithPayment presents a real mined payment and gets the 200 and a successful X-PAYMENT-RESPONSE. It holds only the merchant's incoming viewing key.

  1. GET a paid path → 402 {x402Version: 1, accepts}: the price (maxAmountRequired), a memo nonce in extra.memoNonce, its expiry and a ZIP-321 URI a wallet can open.
  2. The client pays with that memo, then retries with X-PAYMENT: base64({x402Version: 1, scheme, network, payload: {txid, memoNonce}}) (or Hanko's older {memo, txid}).
  3. The gateway checks the payment with verify() → 200 with the receipt in the body and X-PAYMENT-RESPONSE: {success, transaction, network, payer: ""}, or 402 with the reasons.

Guarantees

  • A memo and a txid pay once. Both are claimed before the check is awaited, so two concurrent requests with one payment get one 200 and one 402 (live test). Txids are compared lower-cased.
  • Challenges cost nothing until a payment arrives: the memo is zpv-<expiry>-<nonce>-<HMAC>, so GETs store nothing. 10,000 GETs in a second still leave the next buyer a 402 (test).
  • Mined-time expiry: a payment counts if its block came before the challenge's expiry plus 10 minutes, even when presented later. Later is PAYMENT_LATE.
  • Money that arrives but is refused (underpaid, a transparent part, late) is recorded, the 402 says so, and GET /api/refunds lists it to a request carrying the merchant's ZPV_ADMIN_TOKEN (off without one; where a request comes from is not trusted, since behind a reverse proxy everything looks local). The refund is sent by hand: the gateway holds no spend key.
  • Limits: at most ZPV_MAX_CHECKS (8) checks run at once and 32 wait, the rest get 503 + Retry-After; the paywall's own checks have their own slots, and the production paywall does not serve /api/verify at all (only the verify API does, and only to application/json bodies); a check with no answer is killed after 90 s; a challenge closes after 5 refused payments (not counting TX_NOT_FOUND while lightwalletd has not seen a fresh payment), and a payment that reaches a closed challenge is recorded for a refund (CHALLENGE_CLOSED), never lost.
  • A lightwalletd that is down, inconsistent or outvoted (ZPV_LWD_URLS) gives 503 with Retry-After, never a 400 the client would give up on; nothing is served and the payment stays claimable.
  • State is in memory by default. With ZPV_STORE it lives in one SQLite file: a restarted paywall still refuses a txid it served and accepts the memos it issued, and two paywall processes on one file serve a payment once (live test with a real second process).
  • It will not start with settings that would refuse every payment: ZPV_MIN_CONF 0 or not a number, a price of 0, or a ZPV_PAY_TO that does not belong to the viewing key.

POST /api/verify

The verify API the dashboard calls: the request body is a verify() request for either rail, the response is its result. It listens on 127.0.0.1:8403 and answers CORS only for the origins in ZPV_CORS.

StatusMeaning
200a result: verdict paid, refused or unverified, with reasons
400bad input: not JSON or not an object, unknown rail, amountZat not a whole number ≥ 0, a bad key or txid
502could not check: lightwalletd or Fuji unreachable, or lightwalletd answered inconsistently; with Retry-After
503Setup required (no zpay-verify, a bad setting), or too many checks running (Retry-After)

Surfaces · zpv-mcp

MCP tools

An agent asks before it delivers: did this transaction pay me, and was this null-402 settlement a payment to me. The merchant key comes from ZPV_MERCHANT_UIVK in the server's environment, never from a tool argument, so it never passes through the model. Without it the tool answers Setup required: ZPV_MERCHANT_UIVK.

Replay. A check alone does not use a payment up: the same txid passes every time, and without a memo any past payment to the merchant passes. The tool says so and answers single_use: false, so the agent must record what it accepted. With ZPV_STORE the tool needs a memo and accepts each payment once (a second call is ALREADY_USED), sharing that memory with a paywall on the same file. min_conf cannot go below ZPV_MCP_MIN_CONF (default 1).

A null-402 settlement is paid only if its settle() succeeded, the proof pays your payee signal and amount, and the pool paid your address (expect_recipient). The recipient is required because the pool does not bind it: settle() pays whatever address its caller names, so a proof that names you can be settled to someone else. A reverted or pending one is never paid.

ToolArguments
verify_zcash_paymenttxid, amount_zat, memo? (required with ZPV_STORE), min_conf?
verify_null402_settlementsettle_tx, expect_pay_to, expect_amount, expect_recipient (all three needed for ok)

Set ZPV_MCP_LOG to a file to get one JSON line per call. It holds decrypted memos and amounts, so it is written with mode 0600.

Trust and limits

  • What lightwalletd learns. Each check asks for one txid and the block it names. The operator learns that this payment matters to you, when you asked, and your IP address, which links the payment to you; a cross-check tells every endpoint. ZPV_LWD_PROXY=socks5h://127.0.0.1:9050 (Tor) hides the IP and never falls back to a direct connection; the txid and timing are still seen. Compact blocks alone would hide the txid, but they carry no memo.
  • What lightwalletd is trusted for. Recomputing the txid stops a swap, not a forgery. Proofs, binding signatures and the block's place in the chain are not checked, and the height is what the server says. Anyone can encrypt a note of any value with your memo to your public address, so a lying or intercepted lightwalletd can serve one as mined and get paid. Requiring the txid in the named block catches only an answer that contradicts itself. Plaintext http:// is refused unless the host is loopback.
  • A cross-check turns disagreement into "no verdict", but only endpoints run by different people make it meaningful, and public testnet has one operator. Run your own lightwalletd or Zaino on a full node as one of them.
  • A UIVK reveals every incoming payment to its wallet: amounts, memos, which address received them. Give it only to whoever should see that. The keys in this repo belong to demo-only testnet wallets.
  • Testnet only. The binary decodes testnet keys only.
  • Paywall state (the challenge key, paid memos and txids, refunds owed) is in memory unless ZPV_STORE points at a SQLite file, which is shared by processes on one machine, not across machines.
  • The MCP tool remembers accepted payments only with ZPV_STORE; without it, an agent must track txids itself.
  • No ZIP 311 payment disclosures. The ZIP is a draft without Orchard or Ironwood and without an encoding; the design note says why it waits.
  • Not audited. Portfolio piece; the Zecathon entry is Shielded x402.
