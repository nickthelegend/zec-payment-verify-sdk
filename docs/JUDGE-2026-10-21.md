## Top fixes, ranked by impact / effort

1. **Paywall double-serve race** (high impact, small): reserve the memo and the normalised txid
   synchronously before awaiting the check, and release them if the check refuses. Test: two
   concurrent requests with one real payment (one with an upper-case txid) give exactly one 200.
2. **Unbounded challenge map** (medium, small): drop expired challenges and cap the open ones
   (`maxOpenChallenges`, default 10,000); when full, return 503 instead of growing. Test: cap 3 → the
   4th GET is 503; after the TTL a new one is issued.
3. **null-402 `ok` without binding** (medium, small): `ok` must mean "pays me". Without
   `expect.payTo` and `expect.requiredAmount`, add the reason `UNBOUND`, so `ok` is never true for a
   proof nothing ties to the caller. Test against the real Fuji settle.
4. **Malformed `X-PAYMENT` → 400, not 502** (low, tiny).
5. **False test-count claims** (low, tiny): the README "Run it" block and the landing say "23 live
   tests". Only 20 touch a chain; 3 are offline rule tests. Recount after the fixes.
6. **CI** (medium, small): a GitHub Actions workflow that runs `pnpm test` (live testnet, as locally).
7. **Redesign** (UX, medium): replace the landing-kit page and the shared dashboard frame with Hanko's
   own archetype, an API reference.

Not fixed here, and why: publishing to npm and crates.io (needs Nick's accounts, **BLOCKED**); a
persistent store for the paywall (documented limit; out of scope for a verify SDK); a fully passing
null-402 proof (needs null-402's `NULL402_OPERATOR_KEY`, **BLOCKED**); mainnet (refused by design).

## One bold idea

**ZIP 311 payment disclosures: "I paid you" without anyone's viewing key.** Today the verifier needs
the receiver's UIVK, which reveals *every* incoming payment. A payer-side disclosure proves one
output (its note, memo and value) to a third party. A lender, an auditor or an arbiter could then
check a single payment while the receiver's whole history stays private. Hanko already has the
decryption and rule engine; the disclosure would be a second input shape for the same `check()`.
